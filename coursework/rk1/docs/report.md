## Неделя 3 Программа на Rust

Реализована CLI-программа evently-cli, моделирующая регистрацию на событие ограниченной вместимости и однократный проход по билету. Это небольшая самостоятельная программа, которую можно запустить без блокчейна.

### Модель и конструкции языка

Структура Event хранит название, capacity и Vec<Ticket>. Ticket содержит owner и статус Active или Used. Ошибки представлены enum BookingError: SoldOut, Duplicate, NotFound и AlreadyUsed. Методы возвращают Result, а изменение состояния требует &mut self. Поиск использует итераторы, а данные события сериализуются в JSON.

```
cargo run --manifest-path coursework/rk1/Cargo.toml \
  -p evently-cli -- demo 2

cargo test --manifest-path coursework/rk1/Cargo.toml \
  -p evently-cli
```

### Проверка правил

| Тест | Ожидаемый результат | Факт |
|---|---|---|
| capacity_is_enforced | Второй гость при capacity = 1 получает SoldOut | Пройден |
| duplicate_does_not_consume_seat | Повторная регистрация не увеличивает число билетов | Пройден |
| check_in_is_single_use | Повторный проход получает AlreadyUsed | Пройден |
| unknown_guest_is_rejected | Неизвестный гость получает NotFound | Пройден |

В демонстрации guest-alice получает билет и проходит один раз. Итоговый JSON содержит статус Used; повторный вызов выводит Repeated check-in: AlreadyUsed. Аргумент вместимости ограничен диапазоном 1–5000.

Связь с Solana: явные структуры состояния, enum ошибок, заимствования и проверка переходов используются затем в on-chain программе. CLI не хранит данные между запусками и не заменяет серверную базу Evently.

Доказательства в архиве: cli/src/main.rs; evidence/rust-tests.txt; evidence/rust-cli.txt.

## Неделя 5 Счётчик на Anchor

Anchor-программа evently_lab реализует initialize_counter и increment. Для каждого authority счётчик имеет отдельный PDA с seeds ["counter", authority]. Клиент вычисляет адрес, инициализирует аккаунт, читает значение, отправляет increment и читает состояние повторно [4].

Program ID:

```
DE89mDadLLX5WymVUu1giQZZXXKG72HVKzQVz7QPsSDc
```

Counter PDA:

```
AKNZcyQ446VZQv5sCnDAqVc3wsMGPFpXCp51VGrvRcvf
```

| Поле | Тип | Проверенное значение |
|---|---|---|
| authority | Pubkey | Учебный кошелёк отправителя |
| count | u64 | 0 → 1 |
| bump | u8 | 255 |
| Размер | bytes | 49 = 8 discriminator + 32 authority + 8 count + 1 bump |

### Контроль доступа и переполнения

```
#[account(mut,
  seeds = [b"counter", authority.key().as_ref()],
  bump = counter.bump, has_one = authority)]
pub counter: Account<'info, Counter>,
pub authority: Signer<'info>,
```

Signer требует подпись authority. Seeds и bump связывают переданный адрес с ожидаемым PDA, а has_one проверяет владельца права изменения в сохранённом состоянии. Инкремент использует checked_add и возвращает Overflow вместо переполнения.

Положительная проверка подтвердила увеличение ровно на единицу. Вызов от второго кошелька с тем же account отклонён ограничением Anchor. IDL сгенерирован из программы и используется клиентом; неуспешный вызов не принимается как успешная транзакция.

Доказательства в архиве: programs/evently_lab/src/lib.rs; idl/evently_lab.json; client/run.mjs; localnet-run.json, раздел counter.

| Показатель | Значение |
|---|---|
| Decimals | 2 |
| Выпущено | 100 000 минимальных единиц = 1000 ELAB |
| Переведено второму кошельку | 2500 минимальных единиц = 25 ELAB |

### Последовательность операций

Первой транзакцией создаётся mint account, инициализируются MetadataPointer, mint и metadata. Второй создаются ATA отправителя и получателя, выпускаются токены и отзывается mint authority. Третья выполняет TransferChecked: decimals проверяются вместе с суммой. Клиент затем сверяет оба баланса, supply, отсутствие mint authority и название metadata.

URI метаданных указывает на public/metadata/evently-lab.json в репозитории. Этот JSON также включён в архив; при публикации своей копии проекта нужно использовать собственный доступный URI. Metadata update authority сохраняется у учебного кошелька, поэтому метаданные не заявляются неизменяемыми.

### Связь с билетами Evently

ELAB создан отдельно для задания transfer и не используется как платёжное средство. Билет Evently — другой mint: decimals 0, supply 1, NonTransferable и отозванное право эмиссии. Передаваемость учебного токена не меняет правило непередаваемости билета [6].

## РК1 Концепция и архитектура MVP

Evently решает задачу организации мероприятий: публикация события, регистрация гостя, выдача билета и контроль однократного входа. Web3-компонент позволяет независимо проверить факт выпуска токена и его связь с кошельком. Проверка вместимости и допуска остаётся в серверной системе.

### Разделение ответственности

| Компонент | Ответственность |
|---|---|
| React 19 и Vinext | Каталог, регистрация аккаунта, подключение кошелька, билеты, QR и кабинет организатора |
| Ruby on Rails | Авторизация, роли и ownership, резерв мест, очередь, проверка Solana и атомарный check-in |
| PostgreSQL | Пользователи, события, регистрации, билеты и использованные коды |
| Phantom и Solana | Подпись challenge и транзакций; Token-2022 mint, token account и memo |

### Основной сценарий

Гость входит по email и паролю, затем подтверждает владение кошельком подписью одноразового challenge. Сервер резервирует место. Кошелёк подписывает выпуск непередаваемого Token-2022 и memo с идентификаторами события и регистрации. Rails проверяет подтверждённую транзакцию через RPC и только затем помечает билет confirmed.

На входе организатор подписывает memo, относящееся к конкретному билету. Сервер проверяет подпись, принадлежность токена гостю и права организатора; в транзакции базы данных меняет билет active → used. Второй проход блокируется. Сам токен не кодирует окончательное решение о допуске: его принимает Evently на основании серверного состояния.

### Границы прототипа

Роли прототипа: visitor, organizer, admin. Подтверждение email, реальные платежи и SSO не входят в проверенную реализацию РК1. Counter и Profile PDA демонстрируют отдельные учебные программы; основной билетный поток использует стандартный Token-2022. Факт MVP не означает готовность всех функций ранее обсуждённой продуктовой спецификации.

[Репозиторий Evently](https://github.com/miracleunvrs/evently)

## РК1 Проверки сквозного сценария

Проверка выполнялась 4 октября 2026 года в изолированной базе evently_rk1. Клиент использовал настоящие Ed25519-подписи учебных кошельков и отправлял транзакции локальному Solana-валидатору. Ответы Rails и состояния билета проверялись утверждениями assert.

| Проверяемое действие | Полученный результат |
|---|---|
| Вход visitor, organizer, admin | HTTP 200; роли соответствуют назначенным |
| Подтверждение кошельков | Challenge и проверка подписей: HTTP 200 |
| Создание события организатором | HTTP 201; вместимость 1 |
| Регистрация гостя и проверка Token-2022 | HTTP 201 и 200; билет confirmed |

| Первый check-in | HTTP 200 |
| Повторный check-in | HTTP 409 |

## Воспроизведение и завершение Devnet

### Запуск из архива

Распакуйте каталог evently, установите Node.js, Docker, Rust, Solana CLI 2.3.0 и Anchor CLI 0.32.1. Полные команды находятся в coursework/rk1/README.md. Сначала установите зависимости, создайте собственные учебные ключи и синхронизируйте Program ID, затем соберите программы и IDL.

```
npm ci
npm ci --prefix coursework/rk1
node coursework/rk1/scripts/wallet.mjs
node coursework/rk1/scripts/sync-program-id.mjs
```

Запустите локальный валидатор, выдайте SOL обоим учебным кошелькам и выполните deploy.sh localnet. Клиенты run.mjs и analyze.mjs пересоздадут доказательства лабораторных работ. Для MVP поднимите отдельный API на порту 8001 и выполните client/mvp.mjs. Воспроизводимость не требует раскрытия исходных приватных ключей: новые адреса и signatures будут отличаться.

### Что осталось для полного соответствия

На момент подготовки отчёта учебный адрес в Devnet имеет нулевой баланс. Автоматический запрос тестовых SOL ограничен faucet. После получения тестовых SOL нужно выполнить команды ниже из coursework/rk1 и приложить новые JSON и ссылки Explorer. Покупка SOL и использование Mainnet не требуются.

```
bash scripts/deploy.sh devnet
node client/run.mjs devnet
node client/analyze.mjs devnet
```

Успех подтверждают оба файла devnet-deploy-*.json, файл devnet-run.json с completed_at и успешными проверками, а также реальные Devnet Explorer-ссылки. Пока эти файлы не получены, собственный Devnet-перевод недели 1 и Devnet-деплой недели 4 не считаются выполненными.

### Состав и безопасность архива

Архив содержит исходники Evently, учебные программы, IDL, lockfiles, доказательства запусков и инструкцию защиты. Приватные keypair, пароли, .env, зависимости, дампы базы и локальный ledger исключены. ФИО и группа на титульном листе заполняются перед отправкой преподавателю.

## План демонстрации и вопросы защиты

Предлагаемая демонстрация занимает около семи минут. Это рабочий сценарий подготовки; силлабус не задаёт отдельную длительность защиты РК1.

| Время | Демонстрация |
|---|---|
| 0–1 мин | Проблема Evently, ценность проверяемого билета и разделение базы данных и блокчейна |
| 1–2 мин | Rust CLI и тесты регистрации и повторного входа |
| 2–3 мин | Native программа, счётчик Anchor и изменение значения |
| 3–4 мин | Profile PDA: seeds, bump, owner и отклонение чужой подписи |
| 4–5 мин | Транзакции, ELAB, metadata и перевод 25 токенов |
| 5–7 мин | Билет Evently, check-in, повторный проход и ограничения прототипа |

### Ключевые ответы

Почему нужен PDA? Он даёт воспроизводимый адрес состояния по seeds и Program ID. В профиле право изменения дополнительно проверяется по подписи authority; знание адреса не даёт права записи.

Что обеспечивает single-use? Атомарный переход active → used в Rails/PostgreSQL. Memo фиксирует подписанное действие в блокчейне, но сам по себе не заменяет серверную проверку повторного входа.

Почему токен ELAB переводится, а билет нет? Это разные mint accounts. ELAB нужен для учебного transfer; у билета активировано расширение NonTransferable и supply равен единице.

Что даёт Anchor? Проверки accounts и signer, сериализацию, discriminator и IDL. Правила бизнеса, размеры данных и корректные constraints остаются ответственностью разработчика.

Что нельзя утверждать по этому отчёту? Что локальные signatures существуют в Devnet, что все планы продукта уже реализованы, что передача токена автоматически разрешает вход или что прохождение тестов доказывает отсутствие всех уязвимостей.

Доказательства в архиве: Подробный сценарий и дополнительные вопросы: coursework/rk1/docs/defense.md.
